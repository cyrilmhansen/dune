# PL/M-80 V4.0 oracle infrastructure

This directory preserves small PL/M-80 compiler experiments as evidence for
Runes reverse-engineering work. A fixture records what a particular toolchain
run accepted and emitted. It is distinct from output generated by Runes and
does not, by itself, establish a generalized PL/M ABI rule.

## Proven local environment

The verified setup is the local z80pack Intel Intellec MDS-800 Simulator
Release 1.39 running ISIS-II V4.3, with the ISIS-II PL/M-80 Compiler V4.0,
Object Linker V3.0, and Object Locater V3.0. `OBJHEX` is used to convert the
located output to Intel HEX. This describes the local setup; portability to
other hosts or toolchain images has not been established.

## Canonical media and safe launch

The canonical source images are read-only research inputs. Their recorded
baseline identities are:

| Image | Bytes | SHA-256 |
| --- | ---: | --- |
| `disks/library/isis-ii-43.dsk` | 512512 | `a335f169dd44de5d860911b1c3ae5b1f2804a686d78074139b1838840def27db` |
| `disks/library/hd-isis-sys.dsk` | 3686400 | `c3ee6937b302ccfc9fa9a66a928d9365dab0cf66fc4178b71dc482acf876492a` |
| `disks/library/hd-isis-usr.dsk` | 3686400 | `da1d122e65cd1a6701668b51dd8941bca762eb33a8828c82b408157242dcaa88` |

These hashes are also embedded in the repository launcher. Do not use the
upstream `isisii43-hd` wrapper for research: it hard-links the library images
as simulator drive images, so guest writes can modify the canonical files.

Use the repository helper:

```sh
research/plm80-oracle/tools/run-isisii43-isolated.sh -F
```

The helper changes to the established simulator directory (or
`$RUNES_INTELMDSSIM_DIR` when explicitly set), verifies all three canonical
hashes, removes only old `disks/drivea.dsk`, `drivei.dsk`, and `drivej.dsk`,
then creates independent writable copies using `cp --reflink=auto` with an
ordinary-copy fallback. It launches `intelmdssim` with the supplied arguments.
The helper leaves working images after simulator exit for inspection; cleanup
is explicit. On relaunch it replaces those three disposable drive files with
fresh copies. Never copy working images back into `disks/library/`.

The helper and hash checks are automated. Preserving or removing working
images after a run is a manual decision. A guest-side write test has confirmed
that the working image can change while canonical hashes remain unchanged.

## Console and input procedure

The ISIS-II console is the simulator's Telnet service. Connect explicitly:

```sh
/usr/bin/telnet 127.0.0.1 4010
```

The connection is initially silent; CR alone does not trigger the prompt. Send
exactly one ASCII SPACE byte (`0x20`), with no CR/LF, and wait for:

```text
ISIS-II, V4.3
-
```

Only then submit ISIS-II commands. Keep the console connection open while the
simulator is active; disconnecting it can cause a simulator I/O failure.

Fast console submission has lost characters in observed runs. The established
practice is character-paced input within one console-automation session, not
one agent/tool action per character. This pacing is procedural automation; the
disk launcher does not provide a general console-driving interface.

## Artifact extraction

Guest artifacts are copied with ISIS-II `COPY ... TO :HP:`. The current host
output endpoint is the local UNIX socket:

```text
/tmp/.z80pack/intelmdssim.pt
```

This paper-tape output is a persistent stream. Keep one host receiver connected
for the whole artifact batch. Reconnecting between files can leave ISIS-II
waiting on stale device state. Recent captures record a 120-byte zero leader
and trailer around each payload. Payload boundaries are checked against the
lengths shown by `DIR FOR NAME.*` (or the corresponding recorded artifact
sizes); the leader/trailer are separately checked as zeros where that framing
was recorded. The raw framing stream is not normally retained; the extracted
file payloads are.

The socket path and single-receiver behavior are established by fixture
captures. A polished, general-purpose PTP receiver/extractor is not currently
part of this repository workflow.

## Build pipeline and preserved files

The established ISIS-II command pattern for basename `NAME` is:

```text
PLM80 :F0:NAME.PLM DEBUG XREF
LINK :F0:NAME.OBJ TO :F0:NAME.SAT MAP PRINT(:F0:NAME.LMP)
LOCATE :F0:NAME.SAT TO :F0:NAME.LOC MAP PRINT(:F0:NAME.MAP)
OBJHEX :F0:NAME.LOC TO :F0:NAME.HEX
```

`PLM80` emits the compiler listing and relocatable `OBJ`; `LINK` combines the
object input into `SAT` and writes its `LMP` map; `LOCATE` produces absolute
located `LOC` output and a `MAP`; `OBJHEX` converts the located output to
`HEX`. Exact console transcripts and per-fixture naming are retained in each
fixture.

The current fixture convention includes the exact source, listing, `OBJ`,
`SAT`, `LOC`, `HEX`, linker and locator maps/output, console or capture
evidence, `DISASSEMBLY.md`, `README.md`, and `manifest.json`. The manifest
records the available toolchain/media identities, artifact sizes and hashes,
code/data/stack facts, direct observations, and unresolved questions. Not
every older fixture has identical metadata fields; consult its own manifest.

## Verification status

The recorded per-fixture checks include, where applicable:

- PL/M-80 reports zero program errors;
- extracted artifact byte lengths and SHA-256 hashes match the manifest;
- preserved host source matches the source compiled in ISIS-II;
- located code bytes agree with the recorded address ranges, maps, and
  disassembly;
- canonical image hashes are checked before launch by the helper and have
  been checked unchanged after recorded guest writes/runs;
- `git diff --check`, an isolated fixture/documentation commit, push
  confirmation, and a clean worktree at handoff.

These are evidence-backed checks used in the corpus, not a claim that every
historical fixture has identical capture coverage. The launcher automates
canonical hash verification and working-copy creation; source entry, compiler
commands, console interaction, PTP capture/framing checks, and fixture review
remain procedural.

## Read-only Runes analysis view

The preserved evidence can be inspected through the normal CLI without running
the historical compiler:

```sh
dune exec pli80-analyze -- --oracle-fixture research/plm80-oracle/v4-four-byte-parameters
dune exec pli80-analyze -- --compare-oracle-fixtures \
  research/plm80-oracle/v4-three-byte-parameters \
  research/plm80-oracle/v4-four-byte-parameters
dune exec pli80-analyze -- --compare-oracle-fixtures \
  research/plm80-oracle/v4-byte-return \
  research/plm80-oracle/v4-address-return --full-evidence
```

These views read fixture manifests/artifacts and display preserved facts. They
do not run PL/M tools or infer a generalized ABI.

## Limitations

Individual PLM80 overlay provenance remains partly unresolved: the V4.0 banner
is observed, but not every fixture traced which compiler overlays were opened
or used. The fixture corpus is intentionally incomplete. Some console and PTP
transfer steps remain procedural rather than a polished general harness.
